# Roadmap Update Skill

You are helping update the project's **Feature Roadmap** - both the feature plans in `planning/pods/` (per-pod folders) and the consolidated view in `generated/roadmap.md`.

> **Note**: This skill handles the Feature Roadmap (what features/boulders we're building, in which milestones, and when).
> Sprint-level task execution lives in **ClickUp**, not here.
> For Validation Roadmap updates (hypotheses, BHQs, SHQs), see the validation-review skill.
> For exploring alternative roadmap scenarios, see the roadmap-options skill.

---

## Project Structure

### Source of Truth (authored by humans)
- `planning/product_targets.md` - Milestone definitions, must-have features, success criteria (stable, rarely changes)
- `planning/pods/{pod}/features.md` - Per-pod feature priorities (ranked backlog, updated by pod leads)
- `planning/pods/{pod}/milestone_{ms}.md` - Per-pod milestone sprint allocation
- `planning/pods/{pod}/validation.md` - Per-pod BHQ/SHQ alignment (not all pods have this; dozer and art don't)
- `planning/features/*.md` - Feature specs with estimates, discipline breakdown, implementation approach
- `planning/capacity.md` - Team staffing by discipline and milestone (includes Pod Leadership Summary)
- `planning/feature_registry.md` - Feature-to-source mapping, spec status tracking
- `planning/contentTargets.md` - Content production targets across pods (maps, battles, units, etc.)

### Generated / Consolidated
- `generated/roadmap.md` - **Consolidated Gantt + per-pod summaries** (regenerated by this skill from pod folders)

### Reference
- `planning/dependency_map.md` - Pod and feature dependencies
- `planning/GlobalRules.md` - Cross-project constraints
- `planning/ValidationPlan.md` - Validation hypotheses and SHQs
- `planning/TechnicalDebt.md` - Active tech debt items

## Your Task

### 1. Read Current State
- Read the relevant pod folder files: `planning/pods/{pod}/features.md` for feature priorities, `planning/pods/{pod}/milestone_{ms}.md` for sprint allocation, and `planning/pods/{pod}/validation.md` for validation alignment (if it exists — dozer and art don't have one)
- Read `planning/product_targets.md` for milestone definitions and targets
- Read `generated/roadmap.md` for the current consolidated view and Gantt
- Read `planning/capacity.md` to check staffing feasibility and get pod leadership data
- Read `planning/dependency_map.md` for constraints
- Read `planning/feature_registry.md` to check which features are registered and have specs
- If cross-pod impact is possible, read all pod folders (features.md + milestone files from each)
- Read relevant `planning/features/*.md` if estimates or approach are changing
- Read `planning/TechnicalDebt.md` if features touch systems with known debt
- Read `planning/contentTargets.md` for content pipeline targets, quantities, and milestone deadlines

**Graceful Degradation**: If a pod is referenced in `product_targets.md` but has no pod folder (or the folder is missing key files like `features.md`), flag it as a gap and include a placeholder section in the regenerated roadmap with "[Awaiting Pod Plan]". If other files are missing, note it and continue with available data.

### 2. Gather Updates
Ask the user for:
- Which pod(s) to update?
- Feature status changes (started, completed, blocked)?
- New features to add?
- Priority or timeline changes?
- Features to move between milestones?
- Estimate revisions?

### 3. Validate Changes
- **Check capacity**: Does `planning/capacity.md` support the planned work? Flag overallocation.
- **Check dependencies**: Will changes break dependent pods or features?
- **Check targets**: Do changes affect must-have features in `planning/product_targets.md`? Flag if a must-have is being cut or delayed.
- **Check validation**: Do changes affect SHQs in `planning/ValidationPlan.md`? When pulling validation info, check that SHQ statuses in the pod's `validation.md` match the statuses in `planning/ValidationPlan.md`. If they differ, use the ValidationPlan as authoritative and flag the discrepancy. (Mention if so, but don't update ValidationPlan here.)
- **Check tech debt**: Do any planned features depend on systems with active debt items in `planning/TechnicalDebt.md`? Flag if so.
- Flag risks if you spot them

### 4. Update Pod Files
- Update the relevant `planning/pods/{pod}/features.md` with new priority order, statuses, estimates
- Update the relevant `planning/pods/{pod}/milestone_{ms}.md` if sprint allocation changes
- Update "Last Updated" timestamps
- If a new feature is added:
  - Note that a `planning/features/*.md` doc should be created (or create it)
  - Add the feature to `planning/feature_registry.md` with Pod, Milestone, and "Needs Spec" status

### 5. Update Feature Docs (if needed)
- If estimates changed, update the feature doc's estimate and implementation flow
- If scope changed, update the feature doc
- If discipline needs changed, update the feature doc and flag in `planning/capacity.md`

### 6. Regenerate Consolidated Roadmap
**Always regenerate `generated/roadmap.md` after updating pod files.**

#### Structure of `generated/roadmap.md`

The file follows this order:

1. **Header** - title, last updated, reference links, "do not manually edit" note
2. **High-Level Gantt** - Mermaid Gantt chart with all pods and milestones
3. **Pod Sections** - One section per pod, each containing:
   - Pod lead, producer, eng lead (pulled from `planning/capacity.md` Pod Leadership Summary)
   - Link to pod folder
   - Current/next milestone validation focus: relevant BHQs/SHQs with status (from pod's validation.md if it exists)
   - Feature tables for all milestones that have defined features
4. **Legend** - Gantt visual guide
5. **Update History** - Change log

#### a. Rebuild the Gantt Chart
Follow the Visual Roadmap Rules below. The Gantt is the first content section.

#### b. Rebuild Pod Sections
For each pod, generate a section with this structure:

```markdown
### [Pod Name]

**Pod Lead**: [Name from capacity.md] | **Producer**: [Name from capacity.md] | **Eng Lead**: [Name from capacity.md]
**Pod Folder**: [`planning/pods/[pod]/`](../planning/pods/[pod]/)

**[Next Milestone] Validation Focus**: [1-sentence summary of what this pod is validating]

| Key BHQ | Key SHQs for [Milestone] | Status |
|---------|--------------------------|--------|
| [BHQ ID]: [Short name] | [SHQ IDs and brief descriptions] | [Status] |

**[Next Milestone] Features**:

| # | Feature | Estimate | Status |
|---|---------|----------|--------|
| 1 | [Feature] | X sprints | [Status] |

**[Future Milestone] Features** (if defined in pod folder):

| # | Feature | Estimate | Status |
|---|---------|----------|--------|
| 1 | [Feature] | X sprints | [Status] |
```

**Pod leadership**: Always pull Pod Lead, Producer, and Eng Lead from the Pod Leadership Summary table in `planning/capacity.md`. If the pod folder files list different names, flag the discrepancy.

**Multi-milestone display**: Include all milestones that have defined features across the pod's `features.md` and `milestone_*.md` files. Don't discard future milestone definitions during regeneration. Only omit milestones with no features defined yet.

**Phased planning**: If a pod uses phased planning (e.g., P1-P10 build-up), use a Phase column:
```markdown
| Phase | Feature | Status |
|-------|---------|--------|
| P1 | Infrastructure & Foundation | IN PROGRESS |
| P2 | Map Foundation | NOT STARTED |
```

**Validation data**: Pull validation info from the pod's `validation.md` file (if it exists — Dozer doesn't have one). Cross-check SHQ statuses against `planning/ValidationPlan.md` — use the ValidationPlan as authoritative if there's a conflict.

**Pod model**: 5 active pods (Empire, Metagame, Battle, Social Dynamics, Dozer). Art Pod was closed 2026-04-13 — `planning/pods/art/` only holds a closure marker; do not regenerate an Art pod section in `generated/roadmap.md`. Artist deliverables roll up under each pod's content track per `planning/capacity.md`.

If the pod's `features.md` has no features defined yet, show `[TBD - awaiting feature definitions]`.

#### c. Target Check
After regenerating, verify planned features cover the must-haves from `planning/product_targets.md`.
If there are gaps, add a note in the Update History.

### 7. Summary
- Summarize what changed
- Highlight risks, dependency impacts, or target gaps
- If changes affect Validation Roadmap SHQs, note which ones
- Suggest next steps

## Visual Roadmap Rules

### Mermaid Gantt Syntax

```
gantt
    title [Chart Title]
    dateFormat YYYY-MM-DD
    axisFormat %b '%y
    tickInterval 4week

    section Milestones
    [Name]  :milestone, [id], [date], 0d

    section [Pod Name]
    [Feature Name]  :[status], [id], [start or dependency], [duration]
```

### Status Mapping

| Feature Status | Gantt Status | Visual |
|----------------|-------------|--------|
| Completed | `done` | Gray bar |
| In Progress | `active` | Blue bar |
| Blocked | `crit` | Red bar |
| Not Started | (no tag) | Default bar |

### Task ID Rules

- Pod prefixes: `emp` (Empire), `meta` (Metagame), `bat` (Battle), `soc` (Social Dynamics), `doz` (Dozer), `art` (Art)
- Format: `[prefix][number]` - e.g., `emp1`, `bat3`
- Keep IDs stable across updates

### Parallel Pipelines

When a pod has multiple engineers working in parallel:
- Use sub-IDs: `meta_a1`, `meta_a2` (Pipeline A) and `meta_b1`, `meta_b2` (Pipeline B)
- In the Gantt, parallel tasks share the same start date but run independently
- In the pod section table, add a "Pipeline" column when applicable

### Duration Rules

- Sprint = 14d (2 weeks)
- Use actual estimates from feature docs
- Always confirm with user if estimating

### Content Pipelines

Content production (maps, battles, units, etc.) has its own targets and milestone deadlines defined in `planning/contentTargets.md`. Rather than showing content as a single "ongoing" bar, **break content into milestone-phased bars** so producers can see when each content phase must complete and the next must begin.

For example, instead of one "Map Content Pipeline" bar spanning the entire project:
```
Territory Map Content (14x)    :active, emp_tm, 2026-03-18, 2026-10-13
Live Ops Map Content (8x)     :        emp_lo, 2026-10-14, 2027-02-02
```

Apply the same principle to Battle content, Unit content, and any other pipeline with phased targets:
- Use the milestone deadline from `contentTargets.md` as the end date for each phase
- Include the quantity target in the bar name or details (e.g., "14x Territory Maps")
- If a content type transitions from a fixed target to an ongoing cadence (e.g., Live Ops Battles), note that in the details
- Content bars that have "as many as we can get" targets (no firm number) can remain as single ongoing bars

This also applies to the pod section tables — include a **Content Targets** sub-section showing the phased pipeline with quantities and milestone deadlines.

### Gantt Scope

- Show features/boulders, not tasks
- Include all milestones as diamond markers
- Max ~30 bars for readability
- Consolidate TBD pods into placeholder bars

### When the Gantt Exceeds 30 Bars

- Consolidate future milestone features into single summary bars (e.g., "M&C - 9 features")
- Only show individual bars for the current + next milestone
- Merge ongoing/continuous tracks where possible (e.g., "Battle Content" + "Unit Content" -> "Battle Content Pipeline")
- If still over 30, split into two Gantts: "Near-Term Roadmap" (current + next milestone) and "Full Roadmap" (all milestones, consolidated)

## Notes

- Pod folders (`planning/pods/{pod}/`) are the source of truth for priorities; `generated/roadmap.md` is the consolidated view
- Milestone definitions and targets live in `planning/product_targets.md`, not `generated/roadmap.md`
- When adding features, always update `planning/feature_registry.md` AND check if a `planning/features/*.md` doc exists
- Pod leadership comes from `planning/capacity.md` Pod Leadership Summary — don't hardcode names in the roadmap
- The Gantt is a communication tool - optimize for clarity, not completeness
- Preserve multi-milestone feature definitions from pod folders during regeneration
- Use ValidationPlan.md as authoritative for SHQ statuses, not pod validation.md files
- Check TechnicalDebt.md when features touch affected systems
