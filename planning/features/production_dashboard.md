## Why This Feature

### Problem

Producers currently have no single view of project health. To understand "are we on track?", a producer must:
1. Open `product_targets.md` and mentally map which must-haves are covered
2. Check ClickUp for sprint ticket counts
3. Scan `Last Updated` dates across 8+ planning files for staleness
4. Read `generated/roadmap.md` (a Mermaid Gantt that's hard to parse quickly)
5. Read `planning/ValidationPlan.md` for SHQ progress

This takes 15-20 minutes and produces no shareable artifact. It also means staleness goes unnoticed until a skill warns about it.

### What the Dashboard Must Prove

A static HTML dashboard that gives producers (Tim, Holly, others) an at-a-glance view of:
- **Where we're headed** (milestone goals)
- **Where we are right now** (sprint progress)
- **Whether our planning docs are healthy** (artifact staleness)
- **What we're validating** (SHQ status)
- **What we're building** (feature timeline)

### Relationship to Other Artifacts

This dashboard is **not** the Milestone Checkpoint. The checkpoint is a monthly narrative report summarizing progress against milestone targets. The dashboard is a live-ish status display that a producer can open any time.

```
Dashboard (this)          = "Check engine lights" — at-a-glance, always current
Milestone Checkpoint      = "Monthly mechanic report" — narrative summary, periodic
```

## Scope

### Architecture

Follows the existing `roadmap_sheet` pattern: **template + data separation**.

```
generated/
  dashboard/
    index.html              Static HTML template (CSS + JS embedded, self-contained)
    dashboard_data.js        Data file (regenerated by /production-dashboard skill)
```

- `index.html` is a stable template. Rarely changes. Contains layout, styling, and rendering logic.
- `dashboard_data.js` exports a `DASHBOARD_DATA` object. The skill regenerates this file each run.
- Opening `index.html` in any browser renders the dashboard. No server, no build step, no dependencies.

### Panel Layout (top to bottom)

#### Header
- Project name: **Lotus**
- Current milestone name + end date + days remaining
- Last generated timestamp

---

#### Panel 1: Milestone Goals (the "north star")

**Source**: `planning/product_targets.md` (current milestone section)

Displays:
- Current milestone name, end date, sprint count
- **Must-Have Features** table: Feature name | Pod | Status indicator
  - Status comes from brain authoritative files (pod plans, feature specs). ClickUp sync via `/sprint-summary` keeps these current.
- **Success Criteria** checklist: each criterion with a checkbox state
  - Checked = explicitly marked complete; unchecked = still open

**Visual**: Clean table with status pills (gray / blue / green). Success criteria as a checklist below.

---

#### Panel 2: Sprint Progress

**Source**: ClickUp sprint list (via MCP at generation time) or latest `/sprint-summary` snapshot

Displays:
- Current sprint name (e.g., "Zany Zebras 27")
- Sprint date range
- **Ticket summary**: Total | Open | In Progress | Complete | Blocked
- **Per-pod breakdown**: Mini bar chart showing completion % per pod
- Days remaining in sprint

**Visual**: Large number cards for the summary stats. Horizontal stacked bars per pod (gray=open, blue=in progress, green=complete, red=blocked).

---

#### Panel 3: Artifact Health

**Source**: `Last Updated` dates parsed from all `planning/*.md` files, staleness rules from `operating_cadence.md`

Displays:
- Table of planning artifacts with columns: File | Last Updated | Freshness | Expected Cadence
- Freshness indicator:
  - **Fresh** (green): within expected update frequency
  - **Aging** (yellow): approaching staleness threshold
  - **Stale** (red): past staleness threshold
- Suggested action for stale files (e.g., "Run `/validation-review`")

Files tracked:
| File | Stale After | Suggested Action |
|------|-------------|------------------|
| `ValidationPlan.md` (Last Evaluated) | 3 weeks | Run `/validation-review` |
| `pods/*_Plan.md` (each) | 5 weeks | Run `/roadmap-update` |
| `capacity.md` | N/A (event-driven) | Review if staffing changed |
| `generated/roadmap.md` | 5 weeks | Run `/roadmap-update` |
| `generated/validation_roadmap.md` | 3 weeks | Run `/validation-review` |

**Visual**: Traffic-light table. Red rows jump out immediately.

---

#### Panel 4: Validation Roadmap

**Source**: `planning/ValidationPlan.md` (WH/BHQ/SHQ definitions + statuses)

Displays:
- **Winning Hypotheses** as top-level cards with confidence level + trend arrow
- Under each WH: its BHQs as collapsible sections
- Under each BHQ: its SHQs with status pill and target milestone
- SHQ statuses: Not Started | In Progress | Blocked | Answered
- Overall progress: "X of Y SHQs answered for current milestone"

**Visual**: Hierarchical card layout (WH → BHQ → SHQ). Compact, scannable. Confidence uses a simple Low/Med/High color scale.

---

#### Panel 5: Feature Roadmap

**Source**: `generated/roadmap.md` (parsed Gantt data) + pod plans

This is the key visualization improvement over Mermaid. Displays a **CSS Grid timeline** with:

- **X-axis**: Time (sprint boundaries as columns, labeled by sprint name or date)
- **Y-axis**: Pod swim lanes (Empire, Metagame, Battle, Social Dynamics, Dozer)
- **Boulder bars**: Grouped feature blocks spanning their start→end dates
  - Features are grouped into boulders (major work chunks) for clarity — not every individual task
  - Names should be consistent with feature names used across the brain (feature_registry, pod plans)
  - Color: per-pod (consistent color scheme)
  - Label: boulder/feature name inside the bar
  - Opacity/pattern: active vs. future (active = solid, future = lighter)
- **Today marker**: Vertical red dashed line showing current date
- **Milestone markers**: Vertical lines at milestone boundaries with labels
- **Current sprint highlight**: Light background on the current sprint column

**Visual**: Horizontal swim-lane Gantt chart. Clean, wide, color-coded. Designed to be the "one image" you'd paste into a slide deck. Prioritizes clarity over granularity — a producer should be able to glance at this and understand the shape of the plan.

Sprint columns should be wide enough to read boulder names. If a boulder spans multiple sprints, the bar stretches across them.

## Skill: `/production-dashboard`

### Behavior

1. **Read** all source files (product_targets, pod plans, ValidationPlan, roadmap, capacity, operating_cadence)
2. **Parse** `Last Updated` dates from each planning file
3. **Pull** ClickUp sprint data (current sprint list — ticket counts by status, grouped by the "Lotus Pod" custom field)
4. **Generate** `dashboard_data.js` with structured data for each panel
5. **Report** what was refreshed and flag any issues (e.g., "ClickUp unreachable, using last snapshot")

### Graceful Degradation

| If unavailable... | Behavior |
|-------------------|----------|
| ClickUp MCP unreachable | Sprint panel shows "No sprint data — run `/sprint-summary` first" with last-known snapshot if available |
| A planning file is missing | Artifact health shows "File not found" in red; other panels skip that data |
| ValidationPlan has no SHQ statuses | Validation panel shows structure but all statuses as "Unknown" |
| Roadmap.md doesn't exist | Feature Roadmap panel shows "Run `/roadmap-update` to generate" |

## Implementation Approach

### Phase 1: Template + Skill (MVP)

1. **Create `index.html`** — Self-contained HTML/CSS/JS dashboard template
   - All 5 panels rendering from `DASHBOARD_DATA`
   - CSS Grid roadmap with pod swim lanes
   - Traffic-light artifact health
   - Dark theme
2. **Create `/production-dashboard` skill** — Reads brain files + ClickUp, generates `dashboard_data.js`
3. **Test** — Run skill, open HTML, verify all panels render

### Phase 2: Polish (if useful)

- Add hover tooltips on roadmap bars (feature details, SHQ links)
- Add "last 3 sprints" trend mini-chart to sprint panel
- Add dependency arrows on roadmap (from `dependency_map.md`)
- Export-to-PNG button for slide decks

## Risks

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| Roadmap data in Mermaid format is hard to parse reliably | Medium — roadmap panel won't render | Low | Skill parses the structured pod tables in roadmap.md, not the Mermaid block. Or skill reads pod plans directly. |
| ClickUp MCP unavailable at generation time | Low — sprint panel empty | Medium | Graceful degradation; show last-known data |
| Dashboard becomes yet another stale artifact | High — defeats the purpose | Medium | The artifact health panel is self-aware: if `dashboard_data.js` is old, the header shows a warning. Tie to operating cadence. |
| HTML grows too large to maintain | Medium | Low | Template + data separation means template is stable; only data regenerates |

---

## Resolved Decisions

1. **Sprint ticket grouping**: Use the "Lotus Pod" custom field in ClickUp to group tickets by pod.
2. **Must-have status source**: Lean on authoritative brain files (pod plans, feature specs). ClickUp sync happens via existing skills like `/sprint-summary`.
3. **Dashboard staleness threshold**: 1 week (half a sprint). Header shows warning if `dashboard_data.js` is older than 7 days.
4. **Feature roadmap granularity**: Show boulders (major grouped work chunks), not individual tasks. Prioritize clarity and consistent naming with feature names used across the brain.
